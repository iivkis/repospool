# RGP: продуктовая дорожная карта в 3 этапа

**Дата фиксации:** 31 октября 2026  
**Цель:** превратить RGP (Repository Graph Pack) из проверенного в ограниченном
канале транспортного PoC в полезный, воспроизводимый и безопасный инструмент
для ИИ-агента, поставляемый как поддерживаемый продукт.

Это **канонический краткий план из трёх этапов**. Детальные исследования и
гипотезы из [ROADMAP_v1.1.md](ROADMAP_v1.1.md) не удаляются, но не образуют
альтернативную последовательность продуктовых этапов. Реализованные функции
нужно оценивать по кодовым и экспериментальным доказательствам, а не по
историческим checklist.

## Общие обязательные правила

- Применять [Pragmatic Engineering / KISS / DRY](ENGINEERING_PRINCIPLES.md).
- Текущий RGP — снимок кода и инструмент чтения, **не** LLM-runtime.
  Разрабатывающий агент не должен перекладывать проверку результата на человека.
- Каждый этап завершается **agent-owned E2E**: агент сам собирает RGP,
  восстанавливает/валидирует его и использует Reader на заранее заданных задачах
  с проверяемыми эталонами. Нужны команды, исходный commit, SHA-256, результаты,
  негативные кейсы, ограничения и итог `PASS` / `FAIL` / `BLOCKED`.
- В CI и артефактах нельзя публиковать исходники/секреты без отдельного
  разрешения. Содержимое RGP всегда считается недоверенными данными.
- Результаты benchmark отдельно различают целостность, корректность ответов,
  число вызовов, токены, время и подтверждение происхождения.
  Отсутствующее измерение обозначается `unknown`, не нулём.
- `GO` на следующий этап только после его критериев. Иначе `HOLD` с
  конкретными блокерами или `PIVOT` для неподтверждённой гипотезы.

## Этап 1. Надёжное ядро + доказанная полезность MVP-A

**Цель:** пользователь и агент получают один достоверно описанный,
детерминированный RGP от фиксированного commit и могут безопасно решать
конкретные задачи навигации по исходникам. Не начинать дорогую семантику,
пока не показана польза этого базового пути.

### Реализовать / довести

- [ ] Согласовать версионирование формата и границы совместимости Rust
  Generator/Verifier, Python stdlib Reader и Actions ZIP bootstrap.
- [ ] Закрыть найденные в [ревью](REVIEW_2026-10-31.md) пробелы:
  конфликт временного файла при параллельной генерации; масштабируемость
  `git cat-file` по одному blob и полного чтения blobs в Reader;
  стандартизированные лимиты/ошибки.
- [ ] Проверить замкнутый цикл `generate → verify → Reader.validate →
  tree/read/search/coverage` на *закреплённых* реальных Git-репозиториях.
  Сверить байты и результаты с исходной ревизией.
- [ ] Добавить проверяемые негативные сценарии для повреждения, усечения,
  неверных хешей, небезопасных путей, LFS/submodule/partial, неизвестной
  версии, размера и ограничений результатов.
- [ ] Сохранить воспроизводимые проверки доставки через конкретный
  поддерживаемый GitHub-канал; не переносить подтверждённый предел размера
  на непроверенные каналы.
- [ ] Пройти ранний **Gate B**: агент лично выполняет 12 замороженных задач
  на 3 pinned-репозиториях через baseline GitHub и через RGP, сверяет ответы
  с исходниками, публикует честный журнал источников и затрат. Проверить
  сравнение с учётом загрузки, кеширования и подготовки RGP.
  Дополнительная независимая оценка остаётся обязательной для **официального
  GO Gate B по текущему протоколу**, но не подменяет работу агента.

### Выходные артефакты

Релиз-кандидат `MVP-A`, воспроизводимый тестовый набор RGP,
полный протокол agent E2E, результаты и статус Gate B, документация
поддерживаемых путей доставки, формата и известных ограничений.

**Критерий перехода:** все тесты/CI зелёные; RGP дважды генерируется
идентично при одном commit; Rust/Python обнаруживают валидные и
отрицательные fixtures; агент из **готового RGP** правильно отвечает на
оговорённые задачи и фиксирует доказательства. Для продуктового решения о
семантике Gate B должен достичь обоснованного `GO` по существующему протоколу
(включая независимую проверку заявлений), иначе `HOLD/PIVOT`.

**Статус на 31.10.2026:** **В работе**. Ряд транспортных и форматных
проверок уже существует; README называет систему `v0.1 / transport PoC`.
Gate B остаётся **HOLD**, поэтому этап не закрыт.

## Этап 2. Индексация и полезный для задачи контекст

**Зависимость:** решение Stage 1 / Gate B подтвердило ценность системы.
**Цель:** дать агенту навигацию по определениям, использованиям и
проверяемым зависимостям с понятным покрытием, не изобретая универсальное
«понимание репозитория».

### Реализовать / довести

- [ ] Минимально необходимый индекс: пути, символы, определения,
  диапазоны исходного кода, происхождение данных. Сначала поддержать
  небольшое измеряемое множество языков и конфигураций.
- [ ] Обеспечить вызовы Reader `symbols` / `definitions` / `references`,
  а затем `dependencies` / `impact` только для данных, которые можно
  действительно подтвердить. Индексаторы (Tree-sitter/SCIP) добавлять по
  экспериментально подтверждённой необходимости.
- [ ] Явно учитывать `parsed` / `partial` / `failed` / `unsupported`,
  неразрешённые связи, точные доказательные source ranges и параметры анализа.
  Не превращать импорт/упоминание в гарантированный runtime call graph.
- [ ] Выдавать компактный контекст под задачу и бюджет агента, указывая
  релевантные файлы, тесты и пробелы покрытия; предусмотреть работу
  без семантического индекса.
- [ ] Автоматизировать agent E2E для задач `найти определение`,
  `найти использования`, `выявить затронутые тесты`,
  `объяснить подтверждённый путь зависимостей`.
  Эталонные результаты и допустимые неизвестные фиксировать заранее.
- [ ] Сравнивать новый Reader с MVP-A и базовым GitHub-чтением:
  корректность не ниже baseline, стоимость и задержка измерены
  вместе с созданием/передачей артефакта.

### Выходные артефакты

Версионированный индекс, расширенный Reader API, таблица покрытий,
golden-fixtures для языков, журналы agent E2E и сравнительный benchmark.

**Критерий перехода:** агент лично выполняет предопределённые задачи через
сгенерированный RGP с проверяемыми source references; отсутствующие
отношения возвращаются как неизвестные, регрессий корректности относительно
закреплённого baseline нет, накладные расходы приемлемы для выбранного
сценария. Если индекс не приносит пользы, сохранить простой Reader и
принять `PIVOT`, а не расширять систему ради архитектуры.

**Статус на 31.10.2026:** **Не реализовано**. `schema.sql` и
`docs/INDEX_SCHEMA.md` документируют будущую схему, но генератор
сейчас не выпускает SQLite/семантический индекс.

## Этап 3. Продуктовая эксплуатация и выпуск v1.0

**Зависимость:** поддерживаемый Stage 2 API прошёл целевые сценарии.
**Цель:** воспроизводимая поставка и работа в реальном CI/agent workflow,
включая откаты, инкрементальное обновление и понятные сбои.

### Реализовать / довести

- [ ] Поддерживаемый путь установки/использования Generator и Reader,
  инструкции для разработчика и агента, версия CLI/API/формата,
  правила совместимости и миграции.
- [ ] Проверяемая генерация/обновление RGP для новых commits;
  актуальность по `input_tree_digest`; безопасная атомарная публикация и
  восстановление после неудачных сборок.
- [ ] Практическая интеграция GitHub Actions/поддерживаемого коннектора:
  явная аутентификация, проверка SHA-256 с внешним trust anchor,
  права доступа, срок хранения и допустимые размеры.
- [ ] Нагрузочные, fuzz/security, adversarial и регрессионные тесты:
  большие репозитории, zip bomb, path ambiguity, повторяющиеся объекты,
  неполные snapshots, деградация ресурсов, утечки секретов.
- [ ] Операционные свойства: структурированные ошибки, диагностика,
  наблюдаемость полноты/производительности, инструкции по восстановлению.
- [ ] Агент выполняет финальный **release rehearsal** от чистого
  Git commit: сборка релизного RGP, доставка поддерживаемым путём,
  проверка хеша/подлинности, чтение и решение набора пользовательских задач,
  негативные проверки; сохраняет полный результат.
- [ ] Выпустить документированные ограничения, changelog и v1.0 только
  после прохождения acceptance matrix и действующих product gates.

### Выходные артефакты

Версия `v1.0`, воспроизводимые CLI/Reader и Release Pipeline,
матрица совместимости, отчёт безопасности, полный agent-owned release
rehearsal, эксплуатационная документация.

**Критерий релиза:** предопределённые пользовательские сценарии
самостоятельно воспроизведены агентом на доставленном RGP; контроль
подлинности/целостности и неполноты работает, критические дефекты не
оставлены без решения, CI/регрессии/ресурсные ограничения подтверждены
проверками, недоказанных заявлений нет.

**Статус на 31.10.2026:** **Не начат как продуктовый этап**;
отдельные элементы CI и политики безопасности уже есть и переиспользуются.

## Матрица доказательств (обязательна для каждого этапа)

| Что проверяется | Кто выполняет | Чем подтверждается |
| --- | --- | --- |
| Код и формат | ИИ-агент-разработчик | Команды, exit codes, CI, golden fixtures |
| Конкретный созданный `.rgp` | Тот же агент | Commit, SHA-256, Reader.validate, проверка полноты |
| Достижение целей задачи | Тот же агент | Заранее заданные задания, ответы Reader, независимый от RGP эталон исходного commit |
| Отказоустойчивость | Тот же агент | Негативные cases, коды ошибок, ограничение ресурсов |
| Публичные сравнительные заявления | Агент + дополнительный аудит согласно действующему Gate B | Сырые наблюдения, честный baseline, независимая оценка/аудит при необходимости |

**Правило приёмки:** просьба «пусть пользователь/ревьюер проверит,
работает ли итоговый файл» не закрывает ни одну строку матрицы.
При невозможности запуска агент явно сообщает `BLOCKED`, сохраняет
доступные проверки и не отмечает этап завершённым.
