# Цель RGP: рабочая память об исходниках для Киры в песочнице

**Статус:** канонический продуктовый приоритет. Дата фиксации: 31 октября 2026 года.
Следовать этой цели до явного решения владельца проекта изменить её.
[Три этапа разработки](PRODUCT_ROADMAP.md) раскрывают реализацию, но не меняют
ни целевого пользователя, ни критерий полезности.

## Для кого и зачем

**Первый и главный пользователь RGP — сама Кира, coding-ассистент ChatGPT,
который разрабатывает проекты пользователя через GitHub и работает
с исходниками в своей Python-песочнице.**

RGP создаётся **Кирой для собственных рабочих задач**: быстрее и надёжнее
разбираться в архитектуре небольшого GitHub-репозитория, удерживать
правильный контекст между вызовами источников, находить место изменения
и связанные тесты, **делать меньше ошибок** при правках, ревью и проверке
результата. Цель не состоит в производстве ZIP, внедрении MCP ради MCP
или разработке продукта для абстрактного внешнего агента.

Типичный реальный масштаб: десятки, сотни и приблизительно до 1000
файлов. Большие нагрузки допустимы как проверка безопасности и
технических границ, **но не как самостоятельный продуктовый приоритет**.

## Главный сценарий (dogfooding)

Когда пользователь просит изменить или разобраться с реальным GitHub-проектом,
Кира должна, если поддерживаемый источник доступен:

1. Определить нужный GitHub-репозиторий и зафиксировать **точный commit**.
   Получить RGP через поддерживаемый GitHub-канал, сверить SHA-256 с
   **независимым доверенным источником**, а не только с заголовком ZIP.
2. Поместить проверенный RGP в **собственную Python-песочницу** и открыть
   доверенным Python stdlib Reader. Проверить `validate`, `overview`,
   `coverage`, commit и неполноту снимка; не исполнять исходники из RGP.
3. Для конкретной задачи использовать `tree`, `search`, `read`,
   `rgp_agent_context.py` или импорт Reader из доверенного проекта.
   Выбирать слова поиска из **самой задачи**, а не заранее известных
   правильных файлов. Находить не только нужный участок, но и возможные
   последствия, соседние модули и тесты.
4. Выработать план изменения с проверяемыми `path:line` цитатами.
   **Изменять код через поддерживаемые GitHub-инструменты или рабочую
   копию Git**: RGP является неизменяемым снимком для понимания,
   **не редактором репозитория**. Учитывать актуальность commit и
   изменение `main` после создания снимка.
5. Прогнать применимые тесты и CI, сопоставить результат с ожидаемым
   поведением и проверить, не затронуты ли другие участки.
   Фиксировать ошибки, пропуски и ограничения, а не выдавать
   совпадение текста за семантическую связь.

Если RGP отсутствует, слишком стар, неполон или не может быть достоверно
проверен, **работать через GitHub напрямую**, явно обозначив переход.
Не выдавать работу GitHub за использование RGP. MCP-сервер служит лишь
**необязательным адаптером**. Его запуск внутри Python-песочницы не
регистрирует автоматически инструменты MCP в текущем ChatGPT.

## Как измеряется успех

**Основная метрика:** качество и успешность *настоящих задач разработки*,
а не целостность архива как таковая:

- Кира правильно определяет изменяемые файлы, связанные тесты и
  затронутые участки; её выводы подтверждаются фактическим исходным кодом.
- Меньше неверных изменений, пропущенных зависимостей, повторных исправлений
  и регрессий; результат проверяется тестами и объективными условиями задачи.
- В одной и той же задаче с **RGP в песочнице** и при честном
  **GitHub-baseline с кешем** сравниваются качество, корректность и
  полнота выполнения. Для публичных заявлений об улучшении требуется
  независимая проверка, а не самооценка Киры.

**Вторичные метрики:** фактические обращения к GitHub, повторно
полученные файлы, размер *переданного и отобранного* контекста, токены,
время, затраты на создание/доставку/валидацию RGP. Не считать
отсутствующие измерения нулём. На одной короткой задаче GitHub может
быть выгоднее, и это нормальный результат сравнения.

**Минимальный следующий опыт:** Кира получает **реальную новую задачу
изменения кода** в небольшом проекте, сначала использует RGP для
понимания устройства проекта и влияния правки, затем выполняет изменение
и тесты. Следом нужна сопоставимая задача/изолированная модельная
сессия с прямым GitHub. Считать удачей не число найденных цитат,
а успешную, проверенную реализацию с меньшим количеством ошибок.

## Что НЕ должно отвлекать

- Не оптимизировать 50 000 файлов и большие бинарные архивы без
  выявленной потребности реальных проектов.
- Не строить SQLite/Tree-sitter/SCIP/граф зависимостей из одного желания
  сделать систему сложнее. Добавлять семантику только при наблюдаемой
  проблеме понимания исходников, которую простой Reader не решает.
- Не делать MCP интеграцию самоцелью. В ChatGPT-песочнице
  непосредственный Python Reader может оказаться удобнее.
- Не подменять полезность агента зелёным CI, корректным SHA-256,
  попаданием в искомую строку или собственным «ответ верный».
- Не объявлять **Gate B = GO** на основании показательных пилотов.
  Его отдельные обязательства и статус **HOLD** сохраняются до
  появления требуемых независимых доказательств.

**Решение по приоритету:** функциональность, которой Кира реально
пользуется при работе с GitHub в своей песочнице, и снижение ошибок
идут раньше оптимизации размера, скорости упаковки и вспомогательных
протоколов доставки.
