# Использование RGP для разработки самого RGP

**Приоритет:** Кира сначала читает заголовок и встроенные инструкции единственного файла `REPO_CONTEXT.rgp`, затем запрашивает только нужные диапазоны текста через GitHub-коннектор или Reader.
Это обязательный dogfooding, отражённый в [AGENTS.md](../AGENTS.md).

## Обычный цикл

```sh
python3 scripts/repo_dogfood.py check --repo .
python3 python/rgp_reader.py --artifact REPO_CONTEXT.rgp overview
python3 python/rgp_reader.py --artifact REPO_CONTEXT.rgp tree --prefix python/
python3 python/rgp_reader.py --artifact REPO_CONTEXT.rgp search 'Reader' --prefix python/
python3 scripts/repo_dogfood.py export --repo . --output /tmp/rgp-context
```

Дальше Кира изучает нужные места и тесты, **меняет GitHub-проект
обычными GitHub/Git средствами** и сверяет результаты с реальными
тестами. Исходники из архива считаются недоверенными данными,
их не следует импортировать/запускать. После новой правки
`rgp:check` может вернуть `STALE_SNAPSHOT` до обновления
снимка: нельзя выдавать предыдущий архив за новый код.

## Git-происхождение без SHA внутри RGP

RGP/3.0 содержит только исходный текст и компактный индекс. SHA,
`source_commit` и криптографические подтверждения удалены ради
экономии токенов. Поэтому источник должен быть **получен извне**:
из фиксированного Git-коммита, а подлинность файла проверяется
по Git blob или независимой контрольной сумме.

Публикация использует два коммита:

1. **A**: исходники и настройки проекта.
2. Генерация RGP по исходникам A.
3. **B**: коммит только `REPO_CONTEXT.rgp`.

`scripts/repo_dogfood.py check` получает A по Git-истории,
проверяет ancestry, отсутствие других изменений между A и B,
сравнивает включённые исходные файлы побайтово с Git и
проверяет соответствие локального .rgp файлу в HEAD.
Для обычного потребителя одного только Reader недостаточно:
изменение текста той же длины RGP/3.0 сам не выявляет.

## Автоматическое обслуживание

[`Kira sandbox RGP snapshot`](../.github/workflows/kira-sandbox-rgp.yml)
при обновлении main создаёт снимок точного `GITHUB_SHA`,
проверяет Rust и Python Reader, экспортирует файлы в песочницу,
публикует независимый SHA в Actions summary, загружает ZIP,
а затем **коммитит один файл `.rgp` в main**. GitHub Actions не требуется для чтения файла напрямую из Git.

Бот создаёт commit только при изменении снимка, не переписывает
другие файлы, не использует force push. Коммит бота сделан
с `GITHUB_TOKEN`, поэтому другие workflows обычно не
перезапускаются от этого коммита. Собственная проверка
`repo_dogfood.py check` запускается в том же workflow после
коммита. При отсутствии прав на push последний шаг упадёт;
при этом основной Actions ZIP остаётся доступен как fallback.
Кира сообщает о таком блокере, а не объявляет bootstrap завершённым.

Для локальной регенерации:

```sh
task rgp:refresh
# Проверить новую версию, затем сделать отдельный Git commit,
# меняющий ТОЛЬКО REPO_CONTEXT.rgp. После commit:
task rgp:check
```

Для Pull Request с изменёнными исходниками текущий tracked
RGP может быть рассчитан на `main`, а не на PR; это
**непосредственно фиксируется как stale**. Работать со
снимком базы для понимания контекста, а изменённые файлы
читать прямо из PR и завершать проверкой RGP нового commit.

## Журнал реального использования

Каждый PR отмечает, какие запросы `tree/search/read` были
использованы до редактирования, найденные файлы/тесты,
ошибки/неполноту и одну возможность улучшения автоматизации
(или `не обнаружено`). Не смешивать это с независимым
модельным Gate B: **HOLD** до честной сравнительной оценки.
