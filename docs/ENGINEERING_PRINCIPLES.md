# Инженерные принципы RGP

**Статус:** нормативные правила разработки. Применяются к изменениям кода,
формата, Reader, экспериментов и продуктовой документации.
Операционные инструкции для ИИ-разработчика: [AGENTS.md](../AGENTS.md).

## Приоритет №1: инструмент Киры для собственной песочницы

Кира разрабатывает RGP прежде всего **для самой себя**: применять его
как проверенный источник контекста GitHub-проектов в собственной
Python-песочнице, чтобы лучше понимать код и его влияние,
выбирать правильные изменения и тесты и допускать меньше ошибок.
Это главная продуктовая цель, а не оптимизация размера архива,
MCP как таковой или 50 000 синтетических файлов. Полный критерий
и обязательный сценарий: [PRODUCT_NORTH_STAR.md](PRODUCT_NORTH_STAR.md).

Новые функции приоритизируются по влиянию на реальные задачи
разработки небольших репозиториев (десятки/сотни/около 1000 файлов).
Если доверенный RGP недоступен, использовать прямой GitHub,
не выдавая fallback за успешный опыт RGP. MCP — необязательный адаптер.
Разница в качестве исправлений и количестве ошибок важнее
одного только сокращения вызовов.

## 1. Pragmatic Engineering

Ценность RGP — не в количестве подсистем, а в проверяемом результате:
агент безопасно получает один снимок репозитория, находит нужные исходники
и выполняет заданную задачу не хуже поддерживаемого базового способа.

- Начинать с конкретного пользовательского сценария, критерия успеха и
  минимальной реализации; сначала доказывать полезность, потом усложнять.
- Не добавлять Tree-sitter, SCIP, БД, сервис или LLM orchestration «на будущее».
  Синтаксические/семантические компоненты допустимы только после
  измерения ценности и ограничений простого Reader.
- Решения о новых зависимостях принимать по измеряемому улучшению, стоимости
  сопровождения, безопасности и совместимости с Python stdlib sandbox.
- Если гипотеза не подтвердилась — `HOLD` / `PIVOT`, а не оптимистичный отчёт.
- Продуктовая функциональность должна иметь узкую end-to-end проверку,
  исполнимую разработавшим её агентом.

## 2. KISS — Keep It Simple

- Разделение на Rust Generator/Verifier и Python stdlib Reader сохраняется.
  В RGP нет встроенной модели, агента, платного API или исполняемого кода.
- Прозрачный линейный Reader лучше непроверяемого «умного» индексатора.
  Оптимизация нужна там, где выявлены реальные ограничения объёма/времени.
- Контракты формата и ошибок должны оставаться явными; неподтверждённая
  семантика возвращается как `not_indexed`, `unknown` или `partial`.
- Не дробить небольшие модули без ощутимого эффекта. Дробить большие
  компоненты только по проверяемым зонам ответственности, сохраняя тесты.
- Предпочитать небольшие PR с понятным доказательством результата.

## 3. DRY — Don't Repeat Yourself

- Единые определения статусов, требований, лимитов и интерфейсов
  документировать в соответствующих спецификациях, не плодить
  конкурирующие описания. Канонический *трёхэтапный* продуктовый план:
  [PRODUCT_ROADMAP.md](PRODUCT_ROADMAP.md). Исторический подробный
  [ROADMAP_v1.1.md](ROADMAP_v1.1.md) остаётся справочным.
- Общие сценарии сборки/тестирования поддерживать через Taskfile/justfile,
  а не копировать длинные несогласованные команды в workflow.
- **Исключение:** независимая проверка одних и тех же недоверенных байтов
  средствами Rust и Python намеренна. Не связывать обе реализации общим
  парсером, иначе исчезнет независимый сигнал о расхождениях.
- Избегать абстракций ради устранения пары понятных строк кода.
  Повторение, обеспечивающее независимость тестирования, допустимо.

## 4. Ответственность ИИ-разработчика

**Написание кода не равно завершению задачи.** Агент, который изменил RGP,
обязан самостоятельно:

1. Определить наблюдаемую цель и проверяемые примеры до разработки.
2. Выполнить тесты кода и форматных контрактов, а не только их написать.
3. Создать реальный `.rgp` из закреплённого Git commit, проверить
   валидность, детерминированность, состав и полноту снимка.
4. Использовать **тот же готовый RGP** через доверенный Python Reader,
   чтобы решить целевые задачи (чтение, поиск, переходы по данным, а затем
   синтаксические/семантические запросы, когда они будут реализованы).
5. Сверить ответы с исходными файлами и ожидаемыми результатами;
   зафиксировать ошибки, пропуски, статус покрытия и реальные расходы.
6. Сохранить свидетельства: commit, SHA-256, команды, результаты,
   отрицательные кейсы, ограничения, ссылки на CI и артефакты.

Тесты только на парсинг архива или зелёный CI без проверки пользовательской
цели **недостаточны**. Третье лицо не должно быть необходимым для того,
чтобы агент узнал, удовлетворяет ли его реализация критериям задачи.
При блокировке выполнение маркируется `BLOCKED`, а не `PASSED`.

Независимый ревьюер может подтверждать публичные экспериментальные
заявления (включая действующие условия Gate B), но это дополнительный аудит,
**не замена** самостоятельной проверки агента. Изменение этого правила не
переводит текущий Gate B из `HOLD` в `GO`.

## 5. Запрещённые подмены результата

- Целостность ZIP ≠ подлинность источника.
- Валидный RGP ≠ полный репозиторий.
- Наличие исходников ≠ качественный поиск или понимание кода.
- `not_indexed` ≠ отсутствие зависимостей.
- Самооценка агента ≠ независимая оценка benchmark.
- Экономия обращений к коннектору ≠ доказанная экономия токенов/времени.
- Тесты с синтетическими fixtures ≠ реальная доставка через GitHub-коннектор.

**Definition of Done:** измеримый сценарий пользователя выполнен,
результат самопроверен тем же агентом, подтверждён проверяемыми данными,
а неизвестное и ограничения описаны без вымышленных успехов.
