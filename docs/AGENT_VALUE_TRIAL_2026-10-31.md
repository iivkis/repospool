# Реальный агентский опыт: 12 задач, 3 небольших репозитория

**31 октября 2026.** Это продуктовый опыт о пользе RGP для модели, а не нагрузочный тест. Проверялись закреплённые задачи из `benchmarks/gate_b/plan.json` на репозиториях с **46, 93 и 50 включёнными исходными файлами**.

## Что сделала Кира в этом разговоре

1. Через подключённый GitHub Actions были **повторно скачаны три настоящих ZIP-артефакта**, с отдельно закреплёнными SHA-256. Их общий размер: **396 854 байта**.
2. Для сравнения были действительно вызваны **13 `fetch_file`** с точным Git commit на те же 13 уникальных эталонных файлах. Все **13/13 Git blob SHA-1** совпали с замороженными контрольными значениями. Суммарный размер *содержимого этих файлов*: **336 734 байта**. Это исходные байты, а не измеренный HTTP-трафик с заголовками.
3. Со стороны RGP в этом опыте учтены **6 отдельных целевых обращений к GitHub**: контрольная запись, получение доверенного Reader, список артефактов и три скачивания. Другие вызовы в ходе разработки PR не относятся к сопоставляемым операциям; эта выборка **не является полным провайдерским транскриптом**, независимым опытом или ретроактивной записью вызовов от 29 октября.
4. Модель изучила реально восстановленные исходники RGP, сформулировала ответы на все 12 замороженных вопросов и сверила ориентиры с исходниками GitHub. Ответы ниже являются **одним и тем же авторским опытом модели**, а не двумя изолированными прогонами и не независимой оценкой.
5. В [полном автоматическом Git→RGP→Reader→source-контекст CI](https://github.com/iivkis/rgp/actions/runs/41138784179) **12/12 навигационных задач и 72/72 фрагмента** совпали с исходными Git-объектами на трёх фиксированных SHA. CI **не вызывает модель для ответов** и поэтому **не может** оценивать её качество.

## Фактическая полезность и расходы

| Наблюдение | Прямой GitHub | RGP |
| --- | ---: | ---: |
| Целевых обращений в исследованном сценарии | **13** чтений Git-файлов | **6** операций подготовки/скачивания |
| Передано исходных байтов / ZIP-байтов (разные представления) | **336 734** байта содержимого 13 файлов | **396 854** байта трёх Actions ZIP |
| Локальная работа после первого получения источника | Кеш 13 файлов нужен самому агенту | Не нужны новые GitHub-вызовы для файлов внутри RGP |
| Точный текст исходников на заданных путях | 13/13 Git blob идентификаторов совпали | 12/12 наборов source-evidence, 72/72 фрагмента совпали с Git |
| Токены модели и качество ответа в независимом слепом тесте | **не измерены** | **не измерены** |

**Размер трёх ZIP на 60 120 байт больше**, чем суммарные исходные байты выбранных 13 файлов (**+17,9% к размеру выбранных файлов**). Это не HTTP byte-level A/B, поскольку заголовки, JSON-оболочки и стоимость GitHub Actions не измерялись. **Выигрыша в количестве исходных байтов в данном сценарии не обнаружено.** Заявление «RGP экономит 53,85% вызовов» допустимо лишь как наблюдение о **6 против 13 целевых операций**, не как подтверждённое снижение реальной цены или токенов модели. Вся авторизация, время подготовки ZIP, кеширование и стоимость вычислений должны включаться в реальный сравнительный эксперимент.

Отдельно подготовленный вручную контекст на 12 задач содержал **35 исходных ориентиров, 12 739 байт JSON**. Реальный автоматический Reader-контекст из CI содержал **72 фрагмента, 48 290 байт JSON**, задевая **21 уникальный Git-файл**, а не только 13 эталонных. **Это не доказательство экономии токенов**: и GitHub-клиент может сокращать текст до нужных строк. Это свидетельство текущих накладных расходов и неидеальной релевантности простого лексического поиска.

## Решение для продукта

- **Работоспособность на малом коде: PASS.** Реальный модельный сценарий показал, что RGP достаточно для объяснения кода с проверяемыми исходными строками; CI подтвердил точность выдачи на всех 12 frozen tasks.
- **Доказанная экономия источника / токенов и независимая точность ответов: НЕ ДОКАЗАНЫ.** Если агент решает всего один вопрос и уже умеет запросить нужный GitHub-файл, RGP может оказаться лишним.
- **Правильный следующий шаг к Этапу 2:** выдать модели минимальный контекст по настоящему запросу, затем протестировать на **новых, скрытых для реализации задачах** два независимых запуска одной фиксированной модели: прямой GitHub с кешем и RGP после подготовки. Журналировать исходные вызовы, реальные token usage и время. Оценку ответов проводить слепо по исходному Git.
- **Не делать пока:** дополнительные стресс-тесты на десятки тысяч файлов, построение общего call graph, SQLite/Tree-sitter только ради красивой схемы.

**Gate B = HOLD.** Есть реальное подтверждение полезной source-навигации, но нет основания объявлять RGP лучше прямого GitHub по качеству ответов или полной стоимости.
