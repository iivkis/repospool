# RGP — техническое ревью продуктовой готовности

**Дата:** 31 октября 2026  
**Объект:** `iivkis/rgp`, ветка `main` на момент аудита.  
**Метод:** статический обзор исходников, документации, тестовой структуры,
CI и опубликованных экспериментальных отчётов через GitHub.
**Ограничение:** в этой сессии не удалось клонировать репозиторий,
поэтому локальные `cargo`, Python-тесты и настоящее создание RGP
**не запускались**. Это не динамическое подтверждение работоспособности
и не security penetration test.

## Сводка

**Вердикт: транспортный/форматный PoC, не product-ready v1.0.**
Положительная сторона: есть разделение Rust Generator/Verifier и
trusted Python stdlib Reader, формат с байтовой целостностью,
детерминированный smoke, негативные fixtures, CI и записи транспортных
измерений. Продуктовая ценность и практическая корректность результатов
агента остаются отдельным доказательным обязательством.

В частности, [README](../README.md) прямо указывает статус
`v0.1 / transport PoC`. [Gate B review](GATE_B_REVIEW.md) фиксирует
`HOLD` для самостоятельной, неослеплённой оценки ответов агента.
Ни зелёный unit-test, ни 24 self-scored observations не равны
обоснованному продуктово-релизному решению.

## Приоритетные наблюдения

### P0. Не замкнута проверка результата агентом

**Наблюдение:** [CI](../.github/workflows/ci.yml) проверяет
формат, тесты, fixtures и `generate/verify/read`, но не устанавливает
общего обязательного контракта «разработавший агент лично создал RGP,
решил заранее заданные пользовательские задачи на этом файле, сверил
с источником и сохранил результат». Gate B содержит специальный
экспериментальный протокол, но он ещё `HOLD`.

**Риск:** реализация объявляется завершённой по факту успешной сборки или
по просьбе к другому человеку провести основную проверку.

**Действие:** принять [AGENTS.md](../AGENTS.md) как обязательную политику,
включить агентный goal-level acceptance в каждый релевантный PR.
Повторно выполнять реальный RGP E2E при изменении генератора/Reader.
Для Gate B отдельно сохранить действующие требования к объективности
публичных сравнительных заявлений.

### P1. Индексация и семантика пока спецификация, не функциональность

**Наблюдение:** [INDEX_SCHEMA](INDEX_SCHEMA.md) и
[SQL DDL](../schema.sql) описывают будущее хранилище. Текущий
[Generator](../src/main.rs) выпускает только manifest + blobs;
[Reader](../python/rgp_reader.py) сообщает `not_indexed` и не
предоставляет `definitions/references/impact`.

**Риск:** пользователь ожидает «граф репозитория», а получает
безопасный полнотекстовый снимок. Отсюда неверное позиционирование.

**Действие:** не обещать семантическую навигацию до её реализации и
тестирования; внедрять узкий индекс только после Gate B и измерять
точность/покрытие на проверяемых задачах (Stage 2).

### P1. Масштабируемость Reader и сборки не доказана

**Наблюдение:** [src/main.rs:129–226](../src/main.rs) вызывает
`git cat-file blob` отдельно для каждого исходного blob;
[python/rgp_reader.py:149–242](../python/rgp_reader.py)
проверяет ZIP и складывает содержимое всех blobs в память;
[python/rgp_reader.py:341–384](../python/rgp_reader.py) при поиске
обходит отобранные текстовые файлы и строки заново. Это разумный
PoC-дизайн, но не измеренное поведение на больших репозиториях.

**Риск:** время сборки, объём памяти и latency поиска растут до
неприемлемых для продуктовых сценариев значений.

**Действие:** сначала измерить p50/p95, RSS, время и объём на
заранее выбранных репозиториях. Затем адресно оптимизировать
batch-чтение Git blobs, работу с содержимым Reader и поиск, только
если метрики покажут необходимость. Не вводить сервис/БД без измерений.

### P1. Безопасность публикации ограничена именами файлов

**Наблюдение:** [src/main.rs:98–108](../src/main.rs) использует
консервативные правила имён (`.env*`, `*.pem` и т. п.).
[Модель безопасности](RGP_SECURITY_MODEL.md) прямо говорит, что
это не полноценный secret scanning и не гарантирует безопасность
публикации произвольного репозитория.

**Риск:** генерация приватного RGP и загрузка его в публичные CI
артефакты без отдельной проверки доступа.

**Действие:** сохранить запрет на автоматическую публикацию данных;
задать explicit publication policy и отдельно проверить утечки секретов,
правильность происхождения SHA и права доступа в Stage 3.

### P2. Временный файл генерации потенциально конфликтует

**Наблюдение:** [src/main.rs:249–290](../src/main.rs) пишет
проверяемый артефакт в фиксированное имя
`output.with_extension("rgp.tmp")`, затем переименовывает его.
Два одновременных запуска для одного пути могут использовать один tmp.

**Риск:** гонка, повреждённый или непредсказуемый результат при
параллельной генерации.

**Действие:** добавить тест параллельных запусков и перейти на
уникальный временный файл в той же директории с корректной очисткой;
результат атомарно публиковать только после проверки.

### P2. Документы продукта и технический план требуют разных уровней

**Наблюдение:** [ROADMAP_v1.1.md](ROADMAP_v1.1.md) содержит длинную
последовательность этапов 0–9 и отдельный 3.5. Этот документ полезен
как техническая декомпозиция, но неудобен как единый критерий
«когда продукт готов».

**Действие:** считать
[PRODUCT_ROADMAP.md](PRODUCT_ROADMAP.md) каноническим продуктовым
планом **ровно из трёх этапов**; старую детализацию сохранять
как справочник, не дублировать конкурирующие release gates.

### P2. DRY и KISS требуют точности, а не механического рефакторинга

**Наблюдение:** форматные проверки намеренно дублируются в Rust и
Python. Это нужная независимая кросс-языковая валидация. При этом
сценарии CI/Taskfile/justfile и крупные модули стоит проверять на
дрейф команд, повторение правил и усложнение поддержки.

**Действие:** оставить независимые реализации формата, усилить
golden/parity tests. Убирать избыточные абстракции, а не создавать
«общий фреймворк» ради формального DRY.

## Что уже работает как основа (по репозиторию)

- **Реализовано в коде:** `rgp generate/verify/inspect`,
  pinned Git commit, ZIP/DEFLATE и хеши, trusted Reader
  `overview/tree/read/search/coverage/validate`, Actions ZIP bootstrap.
- **Есть в CI:** `cargo fmt/clippy/test`, Python stdlib unit tests,
  форматы golden fixtures, негативные проверки, cross-language roundtrip,
  deterministic generation и отдельный Nix smoke.
- **Ограничения:** пределы безопасности архива не являются измеренным
  лимитом конкретного коннектора. Отсутствующий индекс/граф
  честно маркируется `not_indexed`.
- **Gate B:** зафиксированы assistant-only замороженные задачи и
  пилот с учётом повторного использования файлов, но по текущему
  протоколу статус **HOLD**. Внешний ревьюер для публичных claim
  не освобождает агента-разработчика от самостоятельной goal-level проверки.

## Рекомендованный порядок

1. **Сначала Stage 1:** агентный E2E с реальным RGP и честный
   Gate B, исправление выявленных конкурентных/масштабных проблем.
2. **Только затем Stage 2:** минимальный индекс и измеримая
   функциональность навигации по связям.
3. **После этого Stage 3:** выпуск, совместимость, безопасность
   публикации, обновление снимков и повторяемый release rehearsal.

Подробные критерии перехода: [PRODUCT_ROADMAP.md](PRODUCT_ROADMAP.md).
