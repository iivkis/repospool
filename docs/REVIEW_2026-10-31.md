# Техническое ревью RGP/3.0 после отказа от ZIP/Base64

**Дата:** 31 октября 2026 года. **Проверенная база:** `main`
`b3e214bbb0bc628bb65ef006d9158ba87ddf5146` до ревью.
**Метод:** GitHub-коннектор: чтение реальных `src/lean.rs`,
`src/main.rs`, `python/rgp_reader.py`, `scripts/repo_dogfood.py`,
канонического roadmap, тестов, CI и опубликованного `REPO_CONTEXT.rgp`.
Это **статическое ревью** и анализ доступных CI-доказательств,
не новая независимая локальная security-экспертиза или модельный A/B.

## Вердикт

**RGP/3.0 технически работает как читаемый снимок исходников; продуктовая
польза и безопасность текстовой доставки ещё недостаточно доказаны.**
Файл больше не содержит ZIP/Base64, длинных SHA-полей, JSON-манифеста
или отдельно публикуемых `.rgpmi`. Основные исходники остаются
буквальным UTF-8 текстом, индекс позволяет отбирать нужные диапазоны.
В опубликованном снимке индекс занимает 2409 байт на 77 файлов,
игнорируются 58 путей. Это **экономия служебных байтов**,
не измеренное снижение токенов на реальных задачах.

Проверки корпуса, 50k и стресса, Rust/Python, MCP и Git-побайтового
сопоставления были зелёными в PR #56. Часть более поздних
вспомогательных CI-заданий может иметь отдельный статус.
Не считать успешные CI-тесты модельной оценкой корректности.

## Обнаруженные риски, упорядоченные по приоритету

### P1. Reader.validate не доказывает подлинность RGP/3.0

В `src/lean.rs` и `python/rgp_reader.py` Reader проверяет
структуру, UTF-8, длины, пути, границы и строит **локальные**
хеши для совместимости API. Но внутри RGP/3.0 отсутствуют
исходный Git SHA, полный SHA и хеши файлов. Поэтому равнодлинная
подмена текста остаётся структурно валидной. Присутствие
`input_tree_digest` в ответе Reader не создаёт независимого
trust anchor: он вычисляется **из полученного файла**.

**Действие:** при доверенной работе закреплять Git revision вне
RGP, проверять Git blob самого RGP или независимо полученный
SHA-256, при необходимости побайтово сравнивать FILE-секции с
нужным source Git commit. Если канал допускает только line-range,
помечать целостность полного файла как **непроверенную**.
Не переносить старые claims о `HASH_MISMATCH` на RGP/3.0.

### P1. Нужна проверка настоящего сценария GitHub-коннектора

Прошлые workflow доказывают генерацию, поиск и сравнение локальных
файлов. Они не измеряют долю служебных токенов, число
`fetch_file` вызовов, поведение пределов line-range или качество
**реальных новых правок агента**. Прямой GitHub-only путь
может оказаться дешевле RGP для короткой задачи.

**Действие:** сравнить RGP/3.0 selective reads с обычным
GitHub `fetch_file` на одинаковых новых задачах и одной модели,
с отчётом о суммарных токенах, стоимости подготовки, количестве
запросов, времени и независимой проверке корректности. Не
объявлять Gate B = GO до выполнения протокола.

### P1. Полнота относится к области после .rgpignore

RGP/3.0 сохраняет число исключений `I` и сам `.rgpignore`,
но не полный список проигнорированных путей. Проверка `snapshot_complete`
не означает, что весь Git tree уже присутствует. Изменение
правил игнорирования может изменить видимый контекст; проверить
его происхождение можно только по pinned Git revision.

**Действие:** в агентах и отчётах явно показывать scoped coverage
и путь чтения исключённого файла напрямую через GitHub.
Не использовать snapshot для секретных/private проектов без
отдельной политики публикации.

### P2. Устаревшие ZIP-эксперименты мешали ориентироваться

Историческая дорожная карта на 67 КБ, отдельный workflow с
Base64 ZIP, тест transport-probe, отчёты по адаптивному ZIP и
устаревшие ссылки в README и документации создавали впечатление,
что ZIP/Actions bootstrap остаётся целевой архитектурой.

**Действие в этом PR:** удалить *неактивные* транспортные
эксперименты, обновить основной план и навигацию по документам.
Исторические материалы доступны в Git history.

### P2. Legacy-Reader и Gate B данные нельзя удалять механически

`python/rgp_reader.py` по-прежнему умеет читать RGP/1.x и 2.x;
`tests/fixtures/v1/`, `scripts/golden_fixtures.py`,
`tests/test_plain_reader.py`, `tests/test_reader.py` и
их регрессионные тесты защищают объявленный контракт.
Датированные `benchmarks/gate_b/observations.*.json`
используют активные `gate_b_review`, `gate_b_decision`,
`gate_b_sensitivity` и unit-тесты. Их удаление уничтожит
воспроизводимый след экспериментального Gate B.

**Решение:** сохранять legacy fixtures и задействованные Gate B
наблюдения. Не добавлять новые ZIP/DEFLATE оптимизации в
генератор RGP/3.0; legacy оставить только в ограниченном
совместимом пути Reader.

## Проверка результата после ревью

- Каноническая [дорожная карта](PRODUCT_ROADMAP.md) должна описывать
  selective UTF-8 reads, `.rgpignore` и **внешний** Git trust.
- [North star](PRODUCT_NORTH_STAR.md) должен различать чтение
  маленьких фрагментов коннектором и полный файл в песочнице.
- README/Taskfile не должны рекламировать удалённый transport-probe.
- Обязательные Rust/Python regression, корпус, golden 1.x/2.x,
  RGP/3.0 и dogfood должны продолжать работать.
- **Gate B остаётся HOLD**. Сокращение bytes или 50k scale не
  заменяет внешнюю оценку результатов реальных задач.
