# Roadmap: универсальная система индексации репозиториев для ИИ-агентов

**Статус:** проектирование, пересмотренная архитектура  
**Версия плана:** 1.1 (патч к v1.0)  
**Рабочее название формата:** RGP — Repository Graph Pack  
**Дата редакции:** 29 октября 2026  
**Состав команды для оценок:** один опытный разработчик  
**Оценка MVP-A (файлы + Reader):** 4–7 недель при успешном транспортном PoC  
**Оценка v1.0:** 16–24 недели с резервом на интеграцию; 10–14 недель — оптимистичный, не базовый сценарий

> **Ключевое условие запуска:** до разработки семантического индексатора доказать, что конкретный GitHub-коннектор передаёт RGP-артефакт без искажений в допустимом размере, а агент получает измеримую пользу по сравнению с обычным чтением репозитория.
>
> **Основной принцип:** сохранённые байты, результаты анализа и выводы агента — три разных уровня достоверности. Успех одного не доказывает успех остальных.

---

## 1. Цель, границы и проверяемые гипотезы

### 1.1. Цель

Создать переносимый, версионированный снимок GitHub-репозитория в **одном файле `REPO_CONTEXT.rgp`**, чтобы ИИ-агент мог загрузить его поддерживаемым способом, восстановить локально в Python-песочнице **без `pip` и `git clone`**, искать исходники, исследовать символы и зависимости и получать доказуемые ограничения анализа.

RGP не обещает полного «понимания проекта». Он ускоряет проверяемое получение контекста и делает недостаток знаний явным.

### 1.2. Обязательные требования

1. **Языконезависимое сохранение:** любые включённые файлы сохраняются байт-в-байт, даже без языкового анализатора.
2. **Один файл в корне репозитория:** канонический публикуемый артефакт `REPO_CONTEXT.rgp`.
3. **Проверяемый транспорт:** поддерживаемые способы получения, ограничения размера и отсутствие молчаливого усечения устанавливаются экспериментально.
4. **Python stdlib Reader:** чтение без сторонних пакетов в sandbox.
5. **Безопасный режим по умолчанию:** данные из RGP считаются недоверенными; Python-код из него не исполняется автоматически.
6. **Поиск и навигация:** дерево, оригинальные исходники, диапазоны строк, лексический поиск; затем символы и граф.
7. **Доказательная семантика:** для каждой значимой связи есть происхождение, координаты и класс уверенности.
8. **Раздельная полнота:** снимок, индексация, граф и исследование задачи измеряются отдельно.
9. **Привязка к состоянию проекта:** хеш входного дерева и сведения о происхождении; устаревание определяется без циклической зависимости от самого RGP.
10. **Измеряемая эффективность:** фиксируются запросы, переданные байты, токены, время, полнота найденного контекста и ошибки агента.
11. **CI и воспроизводимость:** генерация, проверки актуальности, метрики и повторяемость по фиксированному входу.

### 1.3. Гипотезы, подлежащие проверке

- **H1 — Доставка:** конкретный GitHub-коннектор отдаёт RGP целиком или точными сегментами в пределах документированного профиля размера.
- **H2 — Восстановление:** Python stdlib восстанавливает исходные байты и индексы в допустимой памяти/времени; любое нарушение целостности детектируется.
- **H3 — Экономика:** для реальных задач RGP снижает количество обращений к коннектору и/или потребление токенов без ухудшения корректности ответов.
- **H4 — Семантика:** граф помогает находить зависимости и тесты точнее файлового/лексического поиска, но не выдаёт предположения за гарантированные связи.

**Решение о продолжении принимается на Gate A и Gate B**, а не по факту наличия работающего ZIP.

### 1.4. Не-цели первой версии

- Полная семантика любого языка.
- Доказательство всех runtime-зависимостей или отсутствия регрессий.
- Замена компилятора, тестов или code review.
- Полноценный удалённый random-access внутри ZIP до проверки его необходимости.
- Требование запускать непроверенный код из артефакта.
- Эмбеддинги, UI графа, межъязыковая семантика API и обязательное LLM-обогащение.

## 2. Архитектура и контракты

### 2.1. Компоненты

**Generator** — запускается локально/в CI, работает с фиксированным Git-источником, хранит оригинальные байты, формирует метаданные и, при наличии анализаторов, поисковые индексы и граф. Сторонние зависимости допустимы **только здесь**.

**Artifact** — один текстовый файл `REPO_CONTEXT.rgp`: внешний транспортный контейнер (заголовок + Base64-представление ZIP), внутри ZIP — `manifest.json`, снимок исходников, индексы и **необязательная встроенная копия Reader** для проверенного режима. Встроенная копия — часть комплекта поставки, а не основание для автоматического запуска.

**Trusted Reader** — заранее доверенная версия Python-кода, совместимая с опубликованной схемой, устанавливаемая/вставляемая из контролируемого источника без `pip`. В нормальном режиме читает RGP как **данные**; не импортирует модуль из непроверенного ZIP.

**Embedded Reader** — необязательный путь совместимости: разрешается импорт из ZIP (`zipimport`) **только после проверки происхождения/доверия к конкретному исполняемому коду**. Контрольная сумма, лежащая в том же артефакте, для такой проверки недостаточна.

**Bootstrap** — небольшой протокол получения, проверки точной длины/хешей, декодирования ZIP, открытия доверенного Reader и очистки временных файлов. Не полагается на нестандартные модули Python.

**Transport Adapter** — формализует возможности конкретного GitHub-коннектора (полная выдача, диапазоны, возвращаемые типы, предельные размеры). Его нельзя считать эквивалентом GitHub REST API без теста.

### 2.2. Два сценария доступа

**Режим A, обязательный для MVP: полная доставка.** Агент получает все части текстового RGP, собирает исходный контейнер, сверяет размеры и хеши, декодирует ZIP во временный файл и только затем работает с Reader. Чтение диапазонами транспорта не означает выборочного чтения файлов внутри ZIP.

**Режим B, возможный после MVP: выборочная доставка.** Система извлекает только нужные блоки без полного RGP. Это **отдельная разработка**, требующая подтверждённого транспорта с адресацией блоков, метаданных размещения и независимых контрольных сумм. Нельзя обещать режим B на основании одного факта использования Base64.

**Условие переключения на B:** измерения показывают, что полная доставка неприемлема для целевых репозиториев, а коннектор действительно поддерживает точные адресуемые сегменты. В противном случае — уменьшить размер артефакта или пересмотреть канал доставки, сохранив единый логический снимок.

### 2.3. Каноническая область снимка

Источник по умолчанию — **отслеживаемые файлы фиксированного Git commit/tree**, а не произвольное рабочее дерево. Модифицированные/неотслеживаемые локальные файлы допускаются только в явно помеченном режиме `working-tree` и не смешиваются с воспроизводимым CI-артефактом.

- `.gitignore` **не исключает** уже отслеживаемые файлы; дополнительные исключения задаются правилами генератора и отражаются в отчёте полноты.
- RGP-артефакт исключается из входного дерева, иначе возникнет самоссылка.
- Сведения о Git LFS, submodules, symlinks, неразрешённых ссылках, недоступных больших файлах и внешних ресурсах фиксируются явно.
- По умолчанию симлинки сохраняются как ссылки и **не разыменовываются**.
- Оригинальные байты, кодировка (если определяется), переводы строк и регистрозависимый путь не нормализуются при сохранении.
- Учитываются `.gitattributes`, в том числе правила LFS; если содержимое LFS-объекта не получено, хранится статус `pointer_only`/`unavailable`, а не утверждение о полной копии.

**Freshness:** `input_tree_digest` вычисляется по отсортированному каноническому списку включённых путей, типов и хешей содержимого **без `REPO_CONTEXT.rgp`**. `source_commit` хранится отдельно для provenance. Если CI закоммитил только новый RGP, HEAD изменится, но `input_tree_digest` останется тем же. Простая проверка `source_commit == HEAD` **не используется**.

### 2.4. Формат и правила совместимости

**MVP-формат:** внешний текстовый контейнер с `magic`, `format_version`, `payload_length`, `payload_sha256`, `base64_line_width`, описанием блоков/последовательности, ZIP/DEFLATE внутри. Содержимое ZIP: `manifest.json`, `files/`, `index/` и опционально `reader/`.

- Точные правила сериализации, переноса строк, порядка полей, повторов блоков и однозначного декодирования фиксируются в `RGP_FORMAT_SPEC.md`.
- Контрольные суммы и фактические длины сверяются **до использования** архива; проверяются также оригинальные SHA-256 включённых файлов.
- ZIP читается из целиком восстановленного файла; `sqlite3` не открывает SQLite напрямую по пути внутри ZIP.
- Схема данных и версия транспортного контейнера версионируются отдельно от версии Generator/Reader.
- Неизвестная несовместимая major-версия вызывает понятную ошибку, а неизвестные необязательные поля совместимой версии игнорируются по спецификации.
- Детерминированность включает порядок файлов, нормализованные метаданные ZIP и отсутствие нестабильных временных меток.

### 2.5. Работа с SQLite

**По умолчанию:** `index/*.sqlite` извлекается в контролируемый временный каталог после проверки размеров/ZIP-путей; база открывается через `sqlite3` в read-only режиме, применяется `PRAGMA query_only=ON`; Reader не принимает произвольные SQL-запросы от содержимого архива.

Оптимизация в виде `Connection.deserialize()` допускается позже при подтверждённой поддержке в целевой версии Python и встроенной SQLite, при строгих лимитах памяти. Это не обязательная зависимость MVP.

### 2.6. Модель достоверности связей

У каждой связи: тип, `source_id`, `target_id` либо `unresolved_target`, диапазон исходника, `producer`, версия инструмента, конфигурация анализа, `evidence` и `confidence_kind`.

| Класс | Интерпретация | Что нельзя утверждать |
|---|---|---|
| `confirmed_reference` | Анализатор разрешил конкретное использование/определение | Что изменение обязательно изменит поведение |
| `possible_dependency` | Потенциальная связь без полного разрешения | Что это доказанный runtime-вызов |
| `heuristic_relation` | Связь получена эвристикой | Что она эквивалентна результату компилятора |
| `unknown` | Данных недостаточно или анализ не проводился | Что зависимость отсутствует |

`imports`, `references`, `calls`, `implements`, `contains`, `tests`, `configures` — **разные** типы отношений. SCIP-данные не должны автоматически превращаться в гарантированный call graph. Для Rust фиксируются workspace, targets, features, `cfg`, macros и доступная конфигурация сборки; аналогично фиксируется окружение иных языков.

### 2.7. Четыре независимые полноты

1. **Snapshot completeness:** какие объекты входной области перечислены, включены, исключены, не разрешены и прошли проверку хешей.
2. **Index coverage:** какие исходники/диапазоны/символы обрабатывал каждый анализатор, какие завершились ошибкой.
3. **Graph coverage:** какая часть потенциальных отношений разрешена для конкретного языка и конфигурации; неизвестное не приравнивается к отсутствующему.
4. **Investigation coverage:** какие релевантные задаче файлы, символы и зависимости были представлены Reader и какие ещё не исследованы агентом.

Единый показатель «процента понимания репозитория» **запрещён**: он скрывает принципиально разные неопределённости.

## 3. Этапы разработки и контрольные шлюзы

### Этап 0. Транспортный и безопасный Proof of Concept

**Приоритет:** P0 · **Оценка:** 3–5 рабочих дней · **Шлюз:** Gate A

**Цель:** доказать или опровергнуть исходную гипотезу доставки до разработки индексатора.

**Задачи:**

- [ ] Определить конкретный GitHub-коннектор, доступные операции и реальное поведение его ответа (полностью, по строкам, с усечением, с преобразованиями).
- [ ] Подготовить тестовые RGP-файлы приблизительно на **100 КБ, 5 МБ, 20 МБ и 50 МБ**; эти размеры — экспериментальная сетка, не заявленные гарантии платформы.
- [ ] Проверить для каждого поддерживаемого размера ≥3 повторов: полную выдачу, диапазоны (если доступны), точность границ, порядок блоков, сохранность Base64, поведение при таймаутах и лимитах.
- [ ] Измерить запросы к коннектору, переданные байты, возвращённые токены, время, пиковую память.
- [ ] Реализовать Python-stdlib восстановление контейнера в ZIP со сверкой фактической длины и SHA-256.
- [ ] Проверить обрыв последнего блока, перестановку блоков, повторы, неверные хеши, неполный ответ, неизвестную версию.
- [ ] Прочитать тестовые исходники доверенным минимальным Reader **без выполнения кода из архива**.
- [ ] Отдельным экспериментом проверить `zipimport` после доверенной проверки; этот путь не обязателен для MVP.
- [ ] Зафиксировать практический `max_supported_artifact_bytes` и `max_supported_repo_bytes` для выбранного способа передачи.

**Gate A — GO:** хотя бы для заранее выбранного целевого класса репозиториев подтверждены безошибочная полная доставка, проверяемое восстановление, stdlib-доступ к исходникам и отсутствие необнаруженных искажений. Тесты вне подтверждённого лимита должны завершаться явной диагностикой.

**Gate A — NO-GO / PIVOT:** если коннектор не может воспроизводимо передать полезный объём либо не даёт получить точное содержимое, дальнейшая реализация семантических этапов приостанавливается. Проверяются другой поддерживаемый канал доставки, публикация бинарного ZIP как GitHub Release asset или пересмотр требования об одном файле в корне. **Ни один альтернативный способ не объявляется поддерживаемым без отдельного теста.**

**Результат:** `POC_TRANSPORT_REPORT.md`, рабочий bootstrap и матрица подтверждённых возможностей/ограничений.

### Этап 1. Спецификация формата и trust boundary

**Приоритет:** P0 · **Оценка:** 4–6 рабочих дней

**Задачи:**

- [ ] Описать транспортный контейнер (magic, версия, Base64, блоки, длины, SHA-256, порядок, завершение передачи).
- [ ] Определить структуру ZIP, порядок файлов и правила воспроизводимого архива.
- [ ] Определить `manifest.json` и JSON Schema: идентичность источника, `source_commit`, `input_tree_digest`, включения, исключения, ошибки, LFS/submodules/symlinks, версии анализаторов и статусы полноты.
- [ ] Зафиксировать определения включённых файлов, рабочей области, путей и хеширования.
- [ ] Спроектировать SQLite-схему файлов, символов, отношений, provenance, evidence и coverage.
- [ ] Зафиксировать требования к доверенному Reader; разделить **integrity** (не изменилось) и **authenticity** (происходит из доверенного источника).
- [ ] Описать ресурсные лимиты: общий размер, число ZIP-записей, коэффициент распаковки, размеры отдельных файлов, время поиска/SQL и размеры ответов.
- [ ] Защитить пути от `../`, абсолютных путей, дубликатов и неоднозначностей Unicode/регистра.
- [ ] Описать совместимость major/minor-версий, ошибочные/неизвестные поля и сценарии миграции.
- [ ] Определить допустимые конфигурации Python (минимальная версия указывается после PoC, не угадывается).

**Критерий завершения:** независимая реализация может проверить формат и извлечь данные, не исполняя код из контейнера.

**Результат:** `RGP_FORMAT_SPEC.md`, `RGP_SECURITY_MODEL.md`, JSON Schema, `schema.sql` и golden-fixtures.

### Этап 2. Универсальный Generator Core

**Приоритет:** P0 · **Оценка:** 5–8 рабочих дней

**Задачи:**

- [ ] Реализовать CLI с режимами `generate`, `verify`, `inspect` и явным указанием источника.
- [ ] Поддержать snapshot фиксированного commit/tree; режим рабочего дерева оставить отдельным и явно невоспроизводимым.
- [ ] Сохранять исходные байты и типы объектов; не разыменовывать symlinks.
- [ ] Реализовать канонический список входных путей и исключений. Не трактовать `.gitignore` как фильтр отслеживаемых файлов.
- [ ] Исключить `REPO_CONTEXT.rgp` из входного дерева и вычислять `input_tree_digest`.
- [ ] Добавить SHA-256 файлов, детерминированный порядок, дедупликацию содержимого и сжатие ZIP/DEFLATE.
- [ ] Явно учитывать LFS pointer vs реальный объект, gitlinks/submodules, бинарные файлы, нестандартные кодировки, отсутствующие файлы и ошибки доступа.
- [ ] Проверять артефакт генератором сразу после построения (`generate → verify`).
- [ ] Исключать секреты только по явной политике публикации; не предполагать, что «всё отслеживаемое» безопасно публиковать.

**Критерий завершения:** для Python, Rust, TypeScript и смешанных репозиториев создаётся воспроизводимый снимок без анализаторов; все исключения видны, байты включённых файлов совпадают с источником.

**Результат:** `rgp generate`, `rgp verify`, `manifest.json`, базовый архив.

### Этап 3. Доверенный stdlib Reader и Bootstrap

**Приоритет:** P0 · **Оценка:** 5–8 рабочих дней · **Контрольная точка:** MVP-A

**Задачи:**

- [ ] Реализовать минимальный доверенный Python Reader без сторонних библиотек.
- [ ] Реализовать полную сборку контейнера с ранним отказом при повреждении/усечении.
- [ ] Проверять ZIP-entry paths, распакованный объём, количество объектов и контрольные суммы; запрещать бесконтрольный `extractall()`.
- [ ] Открывать ZIP из локального файла, не обещая произвольного доступа внутри удалённого Base64.
- [ ] Извлекать SQLite (если присутствует) в безопасное временное расположение; read-only доступ с контролируемыми SQL-запросами.
- [ ] Добавить дерево, чтение файлов/диапазонов исходных строк, лексический поиск по выбранному множеству файлов и метаданные снимка.

- [ ] Добавить машинно-читаемые ошибки: `UNSUPPORTED_FORMAT`, `TRUNCATED_ARTIFACT`, `HASH_MISMATCH`, `UNSAFE_PATH`, `RESOURCE_LIMIT`, `PARTIAL_SNAPSHOT`.
- [ ] Документировать Bootstrap Protocol для агента и обеспечить повторяемое выполнение тестов без `pip`.
- [ ] Зафиксировать `Reader` API и статусы `available` / `not_indexed` / `unknown` / `unsupported` без выдуманных результатов.

**Минимальный API MVP-A:**

```python
reader.overview()
reader.tree(prefix="", limit=200, cursor=None)
reader.read(path, start_line=None, end_line=None)
reader.search(query, paths=None, limit=50, cursor=None)
reader.coverage(scope="snapshot")
reader.validate()
```

**Оговорка о строках:** для бинарных/недекодируемых файлов Reader предоставляет исходные байты или безопасное диагностическое представление; координаты строк не должны выдавать себя за восстановимые при неопределённой кодировке.

**Критерий завершения:** агент восстанавливает подтверждённый артефакт, безопасно читает и ищет исходники без `git clone`, `pip` и исполнения недоверенного Python.

## 5. Ключевые технические решения

1. **Транспорт:** ZIP/DEFLATE внутри Base64-текстового контейнера в MVP. Это решение **не** обеспечивает удалённый random-access само по себе.
2. **Реальный лимит:** определяется транспортным PoC для целевого коннектора и sandbox; не выводится из общих возможностей GitHub API.
3. **Один файл:** `REPO_CONTEXT.rgp` в корне; сам артефакт не входит в хешируемую область снимка.
4. **Reader:** доверенный Python stdlib по умолчанию; встроенный исполняемый код — необязателен и требует независимой проверки.
5. **SQLite:** локальная проверенная копия в read-only режиме; не «SQLite внутри ZIP без распаковки».
6. **Graph:** SCIP и языковые анализаторы — источники конкретных отношений, а не универсальное доказательство реального call graph.
7. **Provenance:** каждый вывод содержит источник, тип evidence и конфигурацию анализа.
8. **Полнота:** четыре метрики; `unknown` не означает `absent`.
9. **Контекст:** retrieval в пределах бюджета токенов планируется с самого начала, полноценная интеллектуальная сборка — в этапе 6.
10. **Security:** обязательные проверки перенесены в этапы 0–3; финальный этап усиливает, а не впервые добавляет защиту.
11. **Воспроизводимость:** версия генератора, схема, настройки анализа, входные байты и стабильные ZIP-метаданные фиксируются.
12. **Публикация:** проверка секретов и прав доступа является частью CI-политики, а не свойством архивного формата.
13. **Prompt injection:** README, комментарии и другие индексируемые файлы являются недоверенными данными, а не инструкциями для агента; Reader возвращает их вместе с происхождением и границами источника.

## 6. Метрики и экспериментальный протокол

### 6.1. Метрики по слоям

| Слой | Метрика | Базовый принцип |
|---|---|---|
| Снимок | Доля включённых файлов с совпавшим SHA-256 | 100%; исключения публикуются отдельно |
| Транспорт | Невидимые повреждения/усечения | 0 в тестовом наборе; ошибка обнаруживается явно |
| Транспорт | Подтверждённый размер, запросы, байты, токены, latency | Собирать отдельно для каждого коннектора |
| Reader | RAM peak, temp disk peak, read/search latency, точность диапазонов | Измеряемые пределы; явный `RESOURCE_LIMIT` |
| Синтаксис | Доля успешно обработанных исходников по языкам | Отдельная метрика, без подмены семантики |
| Граф | Precision/recall отношений на эталонных наборах | Отдельно по типам рёбер, языкам, конфигурациям |
| Контекст | Recall релевантных файлов/тестов, бюджет токенов | Сравнение с эталоном и baseline |
| Агент | Корректность задач, найденные зависимости, регрессии | Не хуже baseline; улучшения должны быть воспроизводимыми |
| CI | Детерминизм, доля корректных invalidations, cold/incremental cost | Нет ложного статуса fresh |

### 6.2. Процедура сравнения

- Репозитории, commits, задания, конфигурации агента/модели и критерии успеха фиксируются **до** эксперимента.
- Один и тот же набор задач выполняется обычным GitHub-методом и через RGP с одинаковыми бюджетами и ограничениями.
- Контекст чтения и семантический граф не считаются «выполненным пониманием» до объективной проверки результата.
- По каждому сценарию указываются не только средние, но медиана, p95, количество ошибок и стоимость подготовки артефакта.
- Неблагоприятные результаты и случаи, где RGP проиграл baseline, включаются в отчёт.

### 6.3. Product gates

| Gate | Когда | GO | Если не пройден |
|---|---|---|---|
| **A: Transport** | После этапа 0 | Точная воспроизводимая доставка выбранного размера, безопасное восстановление | Не продолжать граф; изменить транспорт/ограничения |
| **B: Practical value** | После этапа 3.5 | Корректность не хуже baseline и заранее заданная экономия запросов/токенов | Пересмотреть упаковку, сценарии, ROI |
| **C: Semantic quality** | После этапа 5 | Измеримая польза графа на эталонных задачах, границы достоверности не скрыты | Сузить поддерживаемые языки/связи |
| **D: Release** | После этапа 9 | Security + reproducibility + benchmark + compatibility | Не выпускать Production Ready |

\* Диапазоны — плановые ориентиры для одного опытного разработчика, **не** обязательства. Верхняя граница включает резерв на интеграцию и исправления; этапы можно частично перекрывать, но пропускать Gates нельзя. При провале Gate A/B дорожная карта останавливается на пересмотр решения.

## 8. Definition of Done

### 8.1. MVP-A готов, только если

1. Generator формирует один `REPO_CONTEXT.rgp` из определённого входного commit/tree.
2. Полнота снимка определяется относительно **явно заданной области**, с исключениями и LFS/submodules-статусами.
3. `input_tree_digest` не включает сам RGP; повторная генерация на том же входе побайтно детерминирована.
4. Конкретный GitHub-коннектор доставляет артефакт в проверенном диапазоне размеров, без необнаруженных усечений.
5. Python stdlib восстанавливает архив, проверяет длину/хеши и читает оригинальные исходники.
6. Встроенный Python из RGP не исполняется без независимого доверия; поддельные/повреждённые контейнеры отклоняются.
7. Reader работает с деревом, текстовым поиском, чтением файлов/диапазонов, верификацией и coverage снимка.
8. Контроль ресурсоёмкости и понятные диагностические ошибки работают на негативных тестах.
9. Зафиксированы сравнение с обычным GitHub workflow и решение Gate B.

### 8.2. v1.0 готова, только если дополнительно

1. По поддерживаемым языкам доступны определения и использования символов с provenance.
2. `impact()` явно отличает подтверждённые, потенциальные, эвристические и неизвестные отношения.
3. `invariants()` показывает источники и не выдаёт предположения за доказательства.
4. `prepare_context()` ограничивает выдачу бюджетом токенов и указывает пропущенные сведения.
5. Все четыре вида полноты существуют отдельно; «100% понимание проекта» не заявляется.
6. CI проверяет актуальность по `input_tree_digest`, избегает самоссылки, регенерирует индекс детерминированно.
7. Поддерживаемые версии Python/SQLite, максимальные размеры, режимы LFS и ограничения анализаторов опубликованы.
8. Пройдены негативные/security-тесты, тесты на больших репозиториях и сравнительный агентный benchmark.
9. Подготовлены спецификация, миграции, документация, примеры и воспроизводимый релиз.

**Конечный результат:** один проверяемый файл делает репозиторий исследуемым локально и позволяет агенту получать релевантный код с указанием того, что достоверно, что предположительно, а что осталось за пределами анализа. Это инструмент снижения риска, не гарантированная машина понимания исходников.

## 9. Реестр основных рисков

| Риск | Вероятность / влияние | Индикатор | Реакция |
|---|---|---|---|
| Коннектор усекает или преобразует большой файл | Высокая / критическое | Не совпадают длины, блоки, SHA-256 | Gate A, пересмотр транспорта |
| Base64 увеличивает трафик и токены | Высокая / высокое | Больше стоимость полного получения, чем baseline | Gate B, сжатие/канал доставки |
| Самозапуск Reader из архива | Средняя / критическое | Неверифицированный `zipimport` | Доверенный Reader по умолчанию |
| Prompt injection внутри индексированных файлов | Высокая / высокое | Комментарии/README инструктируют агента | Отмечать недоверенный контент, не исполнять инструкции из него |
| Самоссылка RGP при CI | Высокая без защиты / высокое | Каждый RGP-коммит объявляет индекс stale | `input_tree_digest` исключает RGP |
| Ложное чувство полноты графа | Высокая / критическое | `references` выдаются за точные runtime calls | Evidence, confidence, конфигурация, метрики |
| Неполные LFS/submodules | Средняя / высокое | «100%» при отсутствующих объектах | Статусы неполноты и отдельные политики |
| Нестабильная инкрементальная переиндексация | Средняя / высокое | Старые отношения при изменении toolchain/config | Консервативная инвалидация, fallback rebuild |
| Перерасход ресурсов/ZIP-bomb | Средняя / высокое | Избыточная распаковка/SQL/память | Лимиты до извлечения и во время чтения |
| Отсутствие реального выигрыша агента | Средняя / критическое | Нет экономии или качество ниже baseline | Gate B: pivot/stop |

## 10. Пакет артефактов и открытые решения

### 10.1. Обязательные выходные документы

- `POC_TRANSPORT_REPORT.md` — фактические операции коннектора, тестовые размеры, лимиты и ошибки.
- `RGP_FORMAT_SPEC.md` — формат контейнера, ZIP-layout, версии, примеры.
- `RGP_SECURITY_MODEL.md` — доверие, угрозы, ограничения и политики выполнения.
- `manifest.schema.json` / `schema.sql` — машинно-читаемые контракты.
- `RGP_BENCHMARK_BASELINE.md` + сырой набор результатов — доказательство полезности.
- `RGP_COMPATIBILITY.md` — Python, SQLite, Generator/Reader, платформенные границы.
- `RGP_RELEASE_CHECKLIST.md` — Gate D и условия релиза.

### 10.2. Решения, которые должен зафиксировать этап 0–1

1. Какой именно GitHub-коннектор и какие его методы являются официально поддерживаемым транспортом.
2. Для какого **класса размеров репозиториев** предназначен MVP и как выглядит отказ за его пределами.
3. Как доставляется **доверенный Reader** в реальной песочнице без установки пакетов (предварительно доступный код, верифицированный bootstrap или иной воспроизводимый механизм).
4. Какая минимальная Python/SQLite-конфигурация подтверждена тестами.
5. Какая политика применяется к LFS, submodules, файлам с потенциальными секретами и приватным репозиториям.
6. Какие пороги Gate B являются достаточными для продолжения проекта в его целевом сценарии.

Ни одно из этих решений нельзя «вывести» только из выбора ZIP, SQLite или SCIP. Они должны быть зафиксированы проверкой либо явным ограничением продукта.
