# Первый реальный dogfooding RGP в Python-песочнице Киры

**31 октября 2026.** Первичный пользователь RGP — сама Кира. Этот
прогон был нужен, чтобы решить реальную задачу разработки: избавиться
от необходимости получать каждый исходный файл отдельно, когда Кира
хочет изучить GitHub-проект стандартными инструментами песочницы.

## Что Кира лично выполнила в своей песочнице

Использован настоящий GitHub Actions ZIP-артефакт
`agent-pilot-rgp.zip` репозитория `iivkis/rgp` на закреплённом
commit `95963a23e2fd1e5eb68a72db3bde849ed7119a7c`.
Внешний доверенный RGP SHA-256 из Git:
`8e5871336d1aaad32d89e6e1b0e581a836d608e7e3e453b10c32b6d586fcaa6f`.
Кира проверила его по фактическим байтам ZIP-вложения.

Затем отдельно через connected GitHub `fetch_file` проверен Git
blob SHA доверенного Reader из этого снимка:
`cb11bd04c346309c038c38e3e5accb540c341139`.
Кира извлекла **только после этой сверки** файл
`python/rgp_reader.py` в собственную песочницу и запустила
`overview`, `tree`, `search` и `read` на проверенном RGP.

Наблюдение: **46 файлов, полный снимок, 239 150 байт исходных
данных**, `index_coverage=not_indexed`. Поиск нашёл
`python/rgp_reader.py`: реализации `Reader.read` и
`Reader.search` и связанные тесты в `tests/test_reader_api.py`.
Следующим шагом Кира реально развернула все 46 файлов в локальное
дерево **с помощью проверенного Reader снимка** и использовала
обычные shell `grep` и `find` для навигации без обращения к
GitHub. Результат:
`/mnt/data/rgp_sandbox_dogfood/first-source-workspace-v2`.
Это был ручной исследовательский прототип; **не утверждается, что
новый `python/rgp_sandbox.py` уже запускался именно в этом
локальном прототипе**. Он отдельно тестировался в CI.

Выявленная проблема: доступный Reader предоставлял только точечные
`read`/`search`. Чтобы использовать общее Python-окружение
песочницы, приходилось повторять экспорт, придумывать локальный
временный код и помнить про Git mode/symlink/trust ограничения.
Первый проход ручного экспорта также обнаружил изменение внутреннего
API Reader между закреплённой ревизией (`_blobs`) и `main`
(`_blob`): это подтверждает, почему нельзя делать продуктовую
интеграцию с необъявленным внутренним полем старого Reader.

## Исправление

Кира добавила `python/rgp_sandbox.py`, который работает
с **актуальным доверенным Reader проекта**:
`RGP → обязательный независимый SHA-256 → Reader.validate →
проверка полноты/бюджета → инертные обычные файлы → provenance`.

Неполные снимки отклоняются без явного разрешения, существующая
папка не переписывается, создаваемые исходные файлы не получают
исполняемые биты, Git-симлинки записываются как обычный текст.
По умолчанию целевой размер: до 1000 файлов и 32 MiB.

контрольными данными в Git. Unit-тесты отдельно проверили негативные
пути, подменённый хеш, неполный снимок и ограничения.

## Чего этот результат не доказывает

- Это **одно настоящее улучшение рабочего процесса Киры**,
  а не независимый тест изменения количества ошибок модели.
- RGP-папка является снимком, а не рабочей Git-копией; реальные
  изменения выполняются через GitHub-инструменты.
- Полученные локально 46 файлов не являются независимым
  модельным плечом baseline. Время и токены модели не измерены.
- Code-side CI использует pinned corpora, а не автоматически
  свежую копию `main`. Совместимость актуального Reader проверена
  штатным CI и реальным 3-repo run.
- Формальный **Gate B остаётся HOLD**.

**Следующий опыт:** Кира берёт новую пользовательскую задачу
GitHub-правки, сначала анализирует её в собственной RGP-папке,
выбирает затронутые тесты, затем вносит изменения через GitHub и
проверяет результаты. Учитывать также успешность и ошибки без
RGP, а не только счётчик найденных файлов.
