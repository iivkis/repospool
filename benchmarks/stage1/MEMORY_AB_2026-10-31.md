# Stage 1: paired generator peak-memory A/B, 31 October 2026

**Result:** memory optimization PASS, RGP/1.0 byte compatibility PASS.
**Interpretation:** major RSS reduction with **mixed latency and substantial
large-tree slowdown**. No unconditional speedup claim.

Evidence:
- [Actual paired same-runner GitHub Actions run 41134613227](https://github.com/iivkis/rgp/actions/runs/41134594691).
- [Independent 50,005-file capacity rerun 41134360958](https://github.com/iivkis/rgp/actions/runs/41134360958).
- [PR #40](https://github.com/iivkis/rgp/pull/40).

## Method

GitHub Actions built `rgp` twice, separately, from the PR's exact
`main` base revision `7f4a3003e7272f3ce1b7402ab51d6411d2b6143f`
and this PR's candidate code. Both binaries ran on the **same GitHub
Actions runner and against the exact same newly created pinned Git
commit for each profile**, with all Git bytes generated by the
agent-owned harness. The harness called the production Rust CLI,
compared the complete RGP byte streams, verified both via Rust and
the independent Python Reader, and checked representative files
against `git show <commit>:<path>`. Only measurements and SHA-256
identities, never generated Git fixtures or RGP bytes, were uploaded.

**The four full RGP byte sequences matched exactly.** The cited
workflow passed as a whole; an earlier experimental four-profile run
reported valid measurements but failed its obsolete three-profile
assertion and is not used as the completion gate. This includes
the prior 50,000-ZIP-member limit and all four source-navigation
sample sets. The three frozen external public repositories also pass
their existing independently pinned byte checks.

## Actual paired measurements

Peak resident set size is the whole Rust generator process,
measured by GNU `/usr/bin/time` on the same runner. Wall time is
observed in milliseconds, **not** a statistical latency comparison.

| Exact Git profile | Baseline peak RSS KiB | Candidate peak RSS KiB | RSS change | Baseline time ms | Candidate time ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2,000 distinct 1KiB files | 26,852 | 16,564 | **−38.31%** | 270 | 390 |
| 12MiB incompressible blob | 109,488 | 51,828 | **−52.66%** | 540 | 980 |
| 12MiB highly compressible text | 109,728 | 51,780 | **−52.81%** | 170 | 160 |
| 50,005 distinct Git files | 187,052 | 90,468 | **−51.63%** | 2,490 | 5,460 |

At the 50k member boundary, **peak memory almost halved**, but
generation wall time more than doubled: **5.46 vs 2.49 seconds**.
It would be incorrect to describe this as a pure performance win.
The 12MiB and 2k runs have mixed time results and cannot be
extrapolated to production with unknown disk bandwidth or workload.

## How memory was reduced

The generator previously held the complete ZIP, the complete Base64
encoding and a growing transport `String` in memory, while keeping
Git blob data alive for verification. It now builds deterministic ZIP
bytes in a uniquely created temporary file, verifies real ZIP
compression-ratio metadata, optionally re-encodes only outlier
members as `ZIP_STORED`, drops source buffers, streams SHA-256, and
writes 57-byte Base64 input blocks as fixed-width 76-character lines
through a 64KiB `BufWriter` into a second unique temporary file.
It retains Rust `verify` **before** atomic rename, with RAII cleanup.

The additional staging writes and file seeks consume disk space and
I/O. Particularly for 50k small files, disk-backed ZIP construction
currently has a significant latency cost. Buffered Base64 output
eliminates avoidable per-line system calls, but does not remove all
ZIP I/O overhead. Future optimization should benchmark the disk
cost separately rather than quietly trading RAM for unreported time.

## Limitations

- Single-run values on GitHub's ephemeral runners; cache effects,
  scheduling, disk performance and execution order can affect timing.
- Time includes Git snapshot processing and CLI generation, **not**
  building the synthetic Git commit, downloading RGP through the
  GitHub connector, token generation or assistant answer quality.
- RSS includes the generator process, not ZIP temp file disk usage
  and not overall CI host memory.
- No statistical claim, token-efficiency claim, blanket speedup claim,
  enterprise-workload generalization, or automatic Gate B approval.
- **Gate B remains HOLD** until the 24 original assistant answers
  are graded independently and 19 original provider calls are
  authenticated against historical tool logs.
