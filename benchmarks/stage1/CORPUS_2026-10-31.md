Resource measurements are **observed**, not a controlled A/B benchmark.
GNU `time` prints elapsed seconds with two decimal places, so small
operations have 10 ms resolution; the reported 0 ms means below that
resolution, not instantaneous execution. Reader times are measured via
`perf_counter_ns`; Python high-water RSS includes the harness itself.
Checkout latency, GitHub connector calls, model tokens, agent-grade answer
correctness and connected-app transport are **not measured** here.

## Verified functional conditions

- Two generated RGP archives from the exact same fixed Git commit are byte
  identical and verified by the independent Rust/Python implementations.
- All 12 task IDs and reference paths are taken from the frozen plan.
  For every reference, the agent's scripted source-navigation checker
  compares Reader blob bytes to independent `git show` output and
  checks Reader `search` / `read` results against exact original lines.
- Tree pagination covers every indexed path without repetition.
- Missing semantically indexed information is not presented as known.
- Deliberate truncation, unknown version and tampered payload hashes fail
  with expected error categories.
- All three jobs uploaded metadata-only `stage1-corpus-<repository>`
  JSON artifacts. No repository source snapshots were uploaded.

## Interpretation / outstanding gates

**This is an agent-owned technical acceptance step, not an independent
natural-language Gate B comparison.** Full Gate B still needs authentic
connector-operation evidence and impartial grading of the task answers.
The three corpus snapshots here are relatively small; they do not establish
worst-case large-repo performance or production memory ceilings. There are
no controlled baseline measurements proving a speedup over GitHub source
retrieval, and no inference token receipts.

**Decision:** Stage 1 technical corpus diagnostic **PASS**;
**Stage 1 product gate: HOLD (Gate B and scale/connector validation outstanding)**.
